02 / 推理到底在做什么

从输入到输出，是一整套计算过程

Token 是模型处理的文本单位，不总是一个字或一个词。下面是文字生成的简化流程；视觉输入还需要视觉编码阶段。

01

输入与编码

请求转成 token，检查协议、参数与上下文；多模态请求还要处理图像。

→ 查询可复用前缀

02

Prefill 预填充

模型处理输入上下文，建立后续生成需要的中间状态。命中缓存可减少部分重复计算。

→ 准备生成状态

03

Decode 解码

根据上下文继续生成 token；批处理、专家并行与草稿验证影响吞吐和延迟。

→ 持续返回 token

04

输出与服务

将 token 解析为正文、工具调用或结构化结果，处理流式传输与错误。

→ 用户收到结果

这是概念示意，不是部署拓扑或性能测试。DeepInfer、部署问答与 deepseek-recipe 分别提供底层实现、系统说明和协议编解码依据。[1][2][12]

模型内部 KV cache

保存注意力计算中的键和值等中间状态，避免生成过程中反复处理过去内容。

服务端前缀缓存

跨请求复用已持久化的相同前缀状态。命中要求 token 前缀匹配缓存单元；共享一份报告，不代表随便换顺序也能命中。[4]

应用层结果缓存

应用直接返回已保存的答案。这是另一种产品设计，需要考虑内容过期与权限，不能当作 KV cache 的解释。

原稿中最需改写的一句：缓存复用的是部分计算状态，输出仍需生成；同一报告由不同人提交，也不能据此推定服务商会跨账号共享缓存。

分开 Prefill / Decode

两阶段的计算与内存访问特征不同，拆开后可分别配置资源。[2] 分析推断 拆开部署还要计入缓存传输、网络与低负载闲置；总成本是否更低、响应是否更快，取决于具体部署。

推测解码与异步调度

草稿先提出多个 token，目标模型验证后接受有效部分。CPU 提前准备下一批工作，与 GPU 计算重叠。两者都要扣除新增开销，不能把各项加速率直接相加。[1][2]

03 / 从开源代码到线上服务

开源了核心引擎，完整服务仍需集成

关键区别不是“有没有缓存”，而是开源引擎能力与生产级缓存系统、路由和运维之间的范围区别。

本次提供

离线推理与核心功能

  • 优化算子、模型与采样运行时
  • 专家并行 EP 与专家负载均衡 EPLB
  • DSpark 推测解码与置信度验证调度
  • 滑动窗口注意力的有界回放、异步调度
  • 结构化输出及部分确定性功能

具体平台与功能限制见 README，不能推定所有硬件行为相同。[1]

未包含完整服务

线上部署仍要补齐

  • 完整的 KV cache 系统
  • 视觉编码 / Prefill / Decode 分离部署
  • Prefill、Decode 的数据并行副本负载均衡
  • 面向业务的鉴权、配额、计费、监控与故障处理

前三项是 README 明列的缺失；最后一项是本页对产品化工作的建议清单，未声称逐文件审计其实现。[1]

公开代码 →仓库与许可可查
部署复现 →需硬件、负载与指标
线上交付 →需稳定性与运维证据
客户付费 →需合同与实际用量
经济收益需成本、回款与续费

官方建议的高效部署单元为约 64 张 Prefill + 64 张 Decode。它不是所有场景都必须达到的最小卡数，更不是“155 万亿 tokens/天”对应集群大小的证明。官方同时说明可以部署 1P + 1D。[2]

DeepInfer 并非凭空替代整个开源生态：官方称其早期主要基于 vLLM，并参考 SGLang、TensorRT-LLM。评估现有栈时，应比较同模型、同硬件、同质量与同延迟目标下的实际结果。[1]

07 / 产业影响与开源动机

效率改善，需要经过几步才能变成收益

以下均为分析推断。公开代码可以观察，管理层真实动机及行业最终利润分配尚不能直接验证。

工程效率改善 →同质量与延迟下测吞吐
单位成本下降 →扣除适配、网络和存储
服务价格变化 →由供需与竞争决定
客户价值变化由完成率与返工决定
生态假说

更多可用的部署渠道

若第三方更容易提供可靠服务，模型被采用的机会可能增加。观察外部适配、可复现部署和真实迁移；仓库热度不能证明收入。

人才与工程反馈假说

技术公开可能带来贡献

观察外部贡献是否合并、缺陷是否修复、性能改进能否复现。招聘吸引力需要招聘或人员数据，不能由“开源有情怀”推定。

竞争与分流假说

API 可能受到替代压力

第三方可用性提高可能分流官方调用，也可能扩展总需求。两个方向都成立；需用户迁移、价格与收入数据判定净效果。

别把技术效率、API 标价、客户账单当成同一个数。成本下降可能被价格竞争抵消，也可能被服务商保留为利润。产业收益如何分配，不能仅凭开源发布确定。

对小团队的可执行验证

  1. 选一类已经发生的重复任务，固定一小组真实样本和合格标准。
  2. 用当前服务和候选服务分别运行，记录合格率、首字等待、完整耗时、重试与人工分钟数。
  3. 从账单和 usage 读取真实费用，再计算“总费用 ÷ 合格任务数”。
  4. 只有持续负载、工程能力和总体成本证据支持自建时，才进入硬件与部署评估。

08 / 对照原稿逐条看

哪些保留，哪些改写？

保留原稿的问题意识与主线；名称、机制、数字和动机各按自己的证据等级处理。点击展开说明。

第二轮融资完成，可能在 2027 年上市媒体消息

10 月 22–23 日报道支持“新一轮融资完成”的消息；2027 年仍是潜在时间表。本次未取得对应公司正式公告或监管批准，两个事件分别看。 [7][8][9]

模型叫 Vista 1 Flash名称纠正
推理框架就是 GPU 资源调度范围补全

推理是执行已训练模型来产生输出；推理框架还包括算子、内存、通信、批处理与输出约束。资源调度只是其中一部分。 [1][2]

服务一名用户，一张 GPU 就能完成增加条件

取决于模型大小、精度、显存及卸载策略。不能将泛化例子理解为 V4.1-Flash 能在任意单卡高效运行。 [1][2]

同一报告缓存后，不必再生成一遍机制纠正

前缀缓存复用中间状态，不是直接拿旧答案。前缀必须匹配已持久化的缓存单元；相同报告也不能保证第二次请求必然命中。 [4]

把 prefill/decode 拆开，效率会更高增加条件

官方说明可分别配置资源、优化阶段延迟。分析推断：缓存传输、网络和调度也有开销，收益要在实际负载下测量。 [2]

先猜一批 token 就不用逐个生成机制纠正

草稿 token 仍须验证；接受率、验证开销与批量影响收益。不是跳过目标模型的正确性检查。 [1][2]

CPU 只需让输入排好队机制纠正

异步调度重叠 CPU 的批次准备与设备执行，减少 GPU 等待。单纯串行排队并不是吞吐优化的完整解释。 [2]

命中 0.003、未命中 0.15、输出 0.6 美元核实保留

均为 Flash 谷时、每百万 token 价格。50 倍只比较两种输入单价，不是整个请求或企业总成本降 50 倍。 [3]

周日人少，所以算谷时定义改写

谷时是官方规定的计费时段，不依赖你判断现场是否繁忙；周末全部属于谷时。 [3]

38 美元每卡每小时，可得稳定收益公司自述

官方使用 revenue（收入）口径；统计窗口、计费收入与标价折算差异、GPU 分母边界不足以支持独立利润审计。 [2]

128 卡一年收入四千多万美元条件外推

算术为 42,608,640 美元。它要求收入率全年不变且分母可比；不是官方披露的 128 卡年度实收。人民币换算还取决于汇率：按假设 7 元/美元计算，约为 2.98 亿元，不能直接说“三个多亿”。 [2]

这是第一次说明推理能赚钱需改写

至少 2025 年 DeepSeek 已披露过推理成本与理论收入，同时说明实际收入更低。因此“第一次”不成立；本次也不是盈利证明。 [6]

没有完全公开，所以在保护 API 生意动机推断

未完整开放线上组件是事实；官方解释包含与内部基础设施强耦合。商业防御可能性可以讨论，但不能替代官方解释。 [1][2]

云厂商和中小企业都会受益条件判断

云厂商需要适配和运维能力；应用企业需要价格或质量改善传导。原稿列举腾讯云、阿里云、字节、硅基流动，只代表候选受益类别，不证明已经采用 DeepInfer。 [1][2]

vLLM、SGLang 等都是 UC Berkeley 开源归属收窄

两者都是开源项目，但不能把相关框架一概归属单一机构。DeepInfer 官方致谢 vLLM、SGLang 与 TensorRT-LLM 的工作。 [1][10][11]
